> 但视频还在后台继续放声音。现在遮罩弹出的同时会**申请系统音频焦点**（和来电时音乐
> 自动停是同一套机制），正在播放的应用会自己暂停；授权「通知使用权」后还能直接
> 给播放器下发暂停指令。系统音量静音只作为**最后兜底、默认关闭**。详见第八·五节。
>

> 弹在它里面的**系统输入法会被遮罩挤掉**——点密码框时键盘"闪一下就没了"，
> 家长连一个字都输不进去（设置界面同理）。现在三处密码输入全部改成
> **应用自绘的数字键盘**（`PinPad.kt`），完全不依赖输入法。详见第八·五节。
>
> **v1.6 修了一个计时失准的 bug**：进程在"使用中"被系统杀掉后，
> 本轮计时的起点会残留成旧值，导致"守护缺席的那段时间"也被算成使用时长
> ——孩子隔很久再拿起平板，可能一开屏就被判定该休息了。
>
> **v1.5 修的是一个安全漏洞**：设置界面只在 `onCreate` 里弹一次密码框，
> 而"把应用隐藏再打开"不会重建 Activity → 密码框永远不再出现，
> 孩子拿到设备从「最近任务」一点就能直接改设置、关掉守护。
> 现在只要离开前台就重新上锁。
>
> **v1.4 修的是保活链的根本缺陷**：原来靠 `onTaskRemoved()` / `onDestroy()` 收到通知后
> 才排复活闹钟，但实测国产 ROM 结束应用时是**直接 SIGKILL，这两个回调一个都不执行**，
> 于是只剩一条 60 秒心跳兜底——表现就是"结束之后十几秒毫无动静"。
> 现在改成**系统里永远挂着一个 15 秒闹钟**，它到点就叫醒服务、服务再排下一次，
> 链条不依赖任何回调。

## 一、工作原理（为什么不用 Root）

```
守护服务（前台服务，每秒采样一次）
      │
      ├── 判断「屏幕点亮 + 已解锁」→ 累计连续使用时长
      │
      └── 达到上限 → 全屏遮罩，两级互为兜底
                       │
                       ├─ 一级：TYPE_APPLICATION_OVERLAY 系统悬浮窗
                       │        层级最高、可吃掉返回键（首选）
                       │
                       └─ 二级：LockActivity 全屏 Activity
                                国产 ROM 拦截悬浮窗时自动降级启用
```

- **判定"正在使用"**：`PowerManager.isInteractive()` + `KeyguardManager.isKeyguardLocked()`。
  只有屏幕亮着**且**已解锁才开始计时，熄屏、锁屏自动暂停。
- **连续计时**：熄屏或离开使用超过「重新计时阈值」后，累计时长归零。防止"玩一会儿歇一会儿"绕过限制。
- **两级遮罩为什么必要**：部分国产 ROM（OPPO ColorOS / vivo OriginOS / 小米 HyperOS）
  会拦截或静默丢弃 `TYPE_APPLICATION_OVERLAY` 悬浮窗。服务会同时尝试两条路：
  悬浮窗加得上就用悬浮窗（最防逃逸）；加不上立刻退到全屏 `LockActivity` 兜底。
  首页「诊断信息」会实时告诉你当前用的是哪一级、以及失败原因。
- **状态持久化**：所有计时状态写在 `SharedPreferences`，进程被系统杀掉后重启也能接着算。

### 1.1 计时口径（举例子看最清楚）

两个参数决定一切：**连续使用时长**（默认 30 分钟）与**重新计时阈值**（默认 5 分钟）。

```
孩子用了 10 分钟 → 关屏 → 过一会儿再开屏
                          │
        ┌─────────────────┴─────────────────┐
        │                                   │
   离开不到 5 分钟                     离开超过 5 分钟
   累计保留 10:00，继续往上加            累计清零，从 0:00 重算
   → 再撑 20 分钟就强制休息            → 又能连用满 30 分钟
```

要注意的几点：

| 情形 | 实际行为 |
| --- | --- |
| **关屏期间** | **不计入**使用时长。计时挂起（`sessionStartWall` 归零），只记一个"我什么时候离开的" |
| **锁屏（屏幕还亮着）** | 同样算"离开"。判据是"屏幕亮 **且** 已解锁"，停留在锁屏界面不计数 |
| **离开刚好 5 分钟整** | 判据是 `> 5 分钟`（严格大于），刚好卡在 5 分 00 秒**不会**清零 |
| **强制休息结束后** | 累计**强制归零**，从 0 重新开始（休息本身就等于一次重置） |
| **跨天** | 目前**没有**"每天累计总量"的概念。中午用满一次、晚上用满一次，都是各自重新算 |

**这套规则的软肋**：阈值 5 分钟相比 30 分钟的上限偏短。
孩子如果发现规律，可以「用 25 分钟 → 关屏 5 分钟 → 再用 25 分钟」，
实质上是"用 5 分钟休息换 25 分钟使用"，比真正强制休息 5 分钟更划算。

要堵这一条，两条路：

1. **把「重新计时阈值」调大**（比如 15~30 分钟）。设置页就能改。
   代价：孩子正常的课间休息也会让累计清不掉，偶尔会被"冤枉"提前休息。
2. **加"每天累计上限"模式**（当天累计亮屏 2 小时，到点就休息，不看连续与否）。
   这是另一套计时口径，需要改代码，目前**没有实现**。

## 二、防止孩子强制结束守护

孩子发现应用在管他之后，通常有三条"破解"路线。三条都做了对应防御：

| 孩子的操作 | 防御手段 | 效果 |
| --- | --- | --- |
| **① 在「最近任务」里把应用卡片划掉** | `android:stopWithTask="false"`；**系统闹钟每 15 秒永续自检**；另有 0.5s/3s/20s 快速复活链 + JobScheduler 通道 | 卡片划掉后服务会**在 15 秒内自动重新启动**，遮罩随之恢复（若 ROM 走了回调，则是 0.5 秒） |
| **② 进系统设置点「强行停止」** | **设备管理员**（多数 ROM 上按钮变灰）+ **惩罚欠账** + 诊断留痕 | **无法阻止**（见 2.5）：被强停后守护必然中断，只能等下次打开 App 时立刻补一次加重的休息。彻底堵住需要「设备所有者」 |
| **③ 在「最近任务」里长按下拉解锁后再划掉** | 系统级的「加锁」需要家长手动设置一次 | 加锁后系统不允许划掉该卡片 |
| **④ 干脆不管它，等它自己消失** | 应用一到前台就自动确保服务在跑 | 重新打开 App 就恢复守护，不会再卡在"未在运行" |

### 2.0 保活是怎么做的（v1.4 重写）

**关键认知：不能依赖任何"回调"。**

v1.3 及以前是"事件驱动"：ROM 移除任务卡片时会调 `onTaskRemoved()`，我们在那里排 0.5 秒后的复活闹钟。
真机实测（OPPO ColorOS）发现——**ROM 结束应用时是直接 SIGKILL，`onTaskRemoved()` 和 `onDestroy()`
一个都不会执行**，复活闹钟根本没机会排上，只剩一条 60 秒的心跳在兜底。
这就是"手动结束后等了十几秒毫无动静"的真正原因。

v1.4 改成**永续自检**，彻底绕开回调：

```
      系统里永远挂着一个 15 秒的精确闹钟
                  │
        到点触发 GuardianService.onStartCommand()
                  │
        ├── 服务还活着 → 顺手排下一次闹钟（自我续期）
        └── 服务已经死了 → 直接把前台服务拉起来（复活）
```

因为**"服务每次启动都会重排闹钟"**这件事本身不依赖任何 ROM 回调，所以这条链永远不会断。
换句话说：只要应用没被置成 `stopped` 状态，它最多 15 秒就会自己回来一次。

**两条通道：**

| 通道 | 周期 | 类型 | 作用 |
| --- | --- | --- | --- |
| 主通道 | **15 秒** | `setExactAndAllowWhileIdle` | 正常情况下的快速复活 |
| 强通道 | **5 分钟** | `setAlarmClock` | 主通道被省电策略延迟时的保险 |
| 快速链 | 0.5s / 3s / 20s | `setExactAndAllowWhileIdle` | ROM 愿意回调时的"秒回"路径（`onTaskRemoved` / `onDestroy`） |
| 任务调度 | 1s 后 + 每 15 分钟 | `JobScheduler`（`setPersisted`） | 与闹钟完全独立的第二条系统服务通道 |

> **强通道为什么用 `setAlarmClock`**：系统的省电策略（Doze / App Standby / 国产 ROM 后台管控）
> 会延迟普通闹钟，但"用户设定的闹钟"是唯一**不会被延迟**的类型，而且它触发时系统会给应用一个
> **临时白名单**，允许在后台启动前台服务。
> **副作用：状态栏会常驻一个小闹钟图标**（系统认为你设了个闹钟）。为了"不能被破解"，这个代价是值得的。

### 2.1 激活设备管理员（一步，30 秒）

打开 App → 「防止孩子强制结束」区块 → 点 **「去激活」** → 系统弹出激活页面 → 点「激活」。

激活后的实际变化：

- `设置 → 应用 → 使用守护` 里的**「强行停止」按钮变灰**，无法点击；
- 卸载前必须先到 `设置 → 安全 → 设备管理器` 取消激活，取消时会弹出家长警告文案；
- 应用只申请了「锁屏」一项设备管理权限，不读取任何个人数据。

在 App 首页「诊断信息」里可以确认：`设备管理员：已激活`。

### 2.2 把「最近任务」卡片加锁（建议做，一次就够）

这是**系统层面的**保护，比任何代码都可靠——加锁后系统直接不允许把该卡片划掉。

| 机型 | 操作 |
| --- | --- |
| **OPPO ColorOS / 一加** | 打开「最近任务」→ 把守护的卡片**向下滑动** → 点出现的**锁形图标** |
| **华为 EMUI / HarmonyOS** | 打开「最近任务」→ 卡片**下拉** → 点**锁形图标**（部分版本需长按卡片） |
| 小米 HyperOS | 打开「最近任务」→ **长按**卡片 → 点锁形图标 |
| vivo OriginOS | 打开「最近任务」→ 卡片**下拉** → 点锁形图标 |

### 2.3 被杀惩罚开关

App 内「防止孩子强制结束」区块的开关：**被强制结束后立即强制休息一次**。

- 原理：服务运行时会持续写"心跳"和"我正在正常运行"两个标记，同时把"疑似被拆防护"
  （强停 / 取消设备管理员 / 划掉任务卡）记成一笔**惩罚欠账**（`Prefs.pendingPenaltyMs`，
  同步 `commit()` 落盘）。账一旦落地，**下次 App 被打开的第一秒**就会兑现成一次强制休息。
- **为什么是"欠账"**：被强停时进程根本没在运行，当场执行等于什么都没做。只有落盘等下次补。
- **力度递增**：第 1 次 1 倍休息时长，第 2 次 2 倍，第 3 次及以后 3 倍（封顶 3 小时）。
  设置区「清除违规记录」按钮可清零。
- **开启前必须先设置家长密码**。否则一旦触发休息，你也会被挡在外面——
  而没有密码时遮罩上根本不显示「家长操作」入口，等于把自己锁死。
- **默认关闭**。原因：家长自己顺手划掉任务卡片也会触发，开启后可能误伤。
  如果孩子确实会这么干，建议打开。
- 首页「诊断信息」里 `后台守护：检测到被结束 N 次  最近一次 14:32:05 · xxx`
  能让你看到孩子到底试过几次、什么时候试的。

### 2.4 说清楚边界：为什么不能 100% 防住

必须诚实地说：**在不做 Device Owner 的前提下，没有任何第三方应用能 100% 抵御一个聪明且耐心的孩子。**

原因很直接——「强行停止」会把应用置为 `stopped` 状态，此时**系统会清空该应用的全部闹钟与
JobScheduler 任务，且不再向它投递任何广播（包括开机广播）**。也就是说：**没有任何代码会被执行**，
不存在"自己爬起来"的可能。设备管理员在多数 ROM 上能让那颗按钮变灰，但孩子仍可去「设备管理器」
取消激活（系统只允许弹一句警告，没有 API 能要求密码），而且部分 ROM（含个别 HarmonyOS 版本）
根本不认设备管理员这一条。

所以 v1.9 起策略从"阻止"改成了"**追责 + 留痕 + 提高代价**"，详见 2.5。

**好消息是：这种情况现在能被自动识别出来。** 应用启动时会把"我们排进系统的闹钟还在不在"
查一遍（`FLAG_NO_CREATE`）——一次性闹钟触发后 PendingIntent 不会消失，所以"查不到"
只可能是被清空了。一旦识别到，诊断区会出现：

```
强行停止：检测到 1 次（最近 17:42:03）
后台守护：检测到被结束 1 次  最近一次 17:42:03 · 应用被「强行停止」，系统清空了全部闹钟与任务
```

看到这一行就说明：**孩子已经会用「强行停止」了，光靠保活代码挡不住，必须走 Device Owner。**

所以实际的防护强度是：

```
不设置任何东西          → 孩子划一下卡片就破了
+ 设备管理员 + 加锁      → 需要孩子知道"设备管理器→取消激活→卸载"这条路径，门槛大幅提高
+ Device Owner（需恢复出厂）→ 真正锁死，无法卸载、无法强行停止
```

### 2.5 被强停之后怎么办：惩罚欠账（v1.9）

强停之后守护必然中断，代码救不回来。那至少要让"这条路"变得不划算，否则孩子发现
"点一下强行停止，就白玩了"之后会一直用。v1.9 的做法是：

```
检测到被强停（或设备管理员被取消）
        │
        ├─ 留痕：次数 +1，并记下时间点（保留最近 10 次，诊断区可见）
        └─ 记账：按策略落一笔「惩罚欠账」（同步 commit，进程随时被杀也不丢）
                        │
                        ▼
        下次 App 被打开的第一秒 → step() 最开头兑现 → 直接进休息
```

几个关键点：

- **欠账而不是立即执行**。被强停时进程根本不在运行，当场执行没有任何东西能显示遮罩。
  只能先落盘，等下次有人把 App 打开时补上——这也意味着孩子强停后**再打开这个 App 就直接进休息**。
- **力度递增**：第 1 次 1 倍休息时长，第 2 次 2 倍，第 3 次及以后 3 倍（封顶 3 小时）。
  孩子已经试了 6 次，说明一次普通休息对他不构成代价。
- **取消设备管理员也算一次**。多数 ROM 上强停的前提就是先取消管理员，所以
  `AdminReceiver.onDisabled()` 里也会记一笔并立刻兑现（那一刻进程还活着，能马上弹遮罩）。
- **家长可以清零**：设置区新增「违规记录」一行和「清除违规记录」按钮，
  同时撤销未执行的欠账，把力度退回"第 1 次"。
- 诊断区新增两行，一眼能看出孩子干了什么：
  ```
  强行停止：检测到 6 次（最近 06:31:12）
  强行停止记录：06:31:12、06:12:04、10-20 21:40:33、10-20 20:55:10
  加固等级：设备管理员（部分机型仍可强行停止）
  ```

### 2.6 终极方案：Device Owner（可选，代价大）


如果孩子已经到了会主动取消设备管理器的程度，唯一彻底的办法是把应用设为
**设备所有者（Device Owner）**。它会带来：无法卸载、无法强行停止、可开启
Lock Task（Kiosk 全屏锁定）。

**代价**：设备必须**恢复出厂设置**，且恢复后不能登录任何小米/华为等厂商账号，然后用 adb 激活：

```bash
adb shell dpm set-device-owner com.huajie.guardian/.AdminReceiver
```

这一步需要另写一套 Device Owner 相关的策略代码（`setUninstallBlocked`、`setLockTaskPackages` 等）。

## 七、先跑一次测试

### 7.1 测遮罩

1. 打开「开启守护」开关。
2. 点 **「立即测试一次强制休息」**，屏幕应立刻被全屏遮罩挡住。
3. 验证：返回键出不去 ✅ / Home 键桌面被遮住 ✅

### 7.1.1 测家长密码（v1.7 改成了自绘键盘）

在遮罩上点 **「家长操作」** → 直接弹出**应用自带的数字键盘**（不会再出现"键盘闪一下就没了"）。

- 位数输满**自动校验**，不用点确定；输错了会提示还剩几次机会；
- 连续错 5 次 → 冷却 60 秒（期间怎么输都不校验）；
- 输对后出现「跳过本次休息 / 暂停守护」两个按钮，**60 秒内有效**，超时自动重新上锁。

> 如果这里键盘还是不出现，说明是别的窗口把遮罩挡住了，
> 把首页「诊断信息」里的「最近一次错误」发我。

### 7.2 测保活 A：自检按钮（验证通道本身是通的）

点 **「自检：模拟进程被杀，看能否自动复活」** → 确认。

它会先把复活通道排好，然后**立刻结束自己的进程**。

| 观察点 | 说明 |
| --- | --- |
| 约 1~3 秒后**通知栏的守护通知重新出现** | 复活成功 ✅ |
| 重新打开 App，诊断区出现 `最近启动：… · 来源 保活闹钟` | 是闹钟拉起来的，不是靠你手动开 ✅ |
| 若开了惩罚开关，重开后**直接进入一次休息** | 惩罚链路也通了 ✅ |

> 注意：这个测试里应用被结束前**在前台**，所以系统会放行。它只能证明"通道通"，
> **不能**证明"在后台被结束也能复活"——那要看 7.3。

### 7.3 测保活 B：手动结束（真正的实战场景，重点看这个）

1. 先打开别的应用（比如浏览器），让守护退到后台，**等 1 分钟**。
2. 打开「最近任务」，把守护的卡片**划掉**（或进 `设置 → 应用 → 使用守护` 点「结束运行」）。
3. 什么都别做，**盯着通知栏数 20 秒**。

预期：**通知栏的守护通知会在 15 秒内自己回来。**

然后重新打开 App 看「诊断信息」，重点看两行：

| 诊断显示 | 含义 | 该怎么办 |
| --- | --- | --- |
| `上次中断时长：15 秒` 左右 | 主通道正常工作 ✅ | 不用做任何事 |
| `上次中断时长：4~5 分钟` | 主通道被省电策略延迟了，只有强通道在工作 | 去第五节把**电池优化白名单**打开（App 里有按钮），能显著改善 |
| `上次中断时长：几十分钟` | 闹钟基本废了，是你手动打开 App 才恢复的 | 系统设置严重不足，第五节逐项做完，特别是「自启动 / 关联启动 / 后台活动」 |
| `强行停止：检测到 N 次` | 孩子（或你）用的是「强行停止」，不是划卡片 | 保活代码挡不住这个，去激活设备管理员；若孩子会取消激活，只能上 Device Owner（2.5） |
| `保活通道：已失效` | 我们的闹钟被系统清空了 | 同上 |

**如果遮罩没出现**（只见应用内倒计时在走），看首页「诊断信息」：先确认 `悬浮窗权限：已开启`
（OPPO 授权后建议重启一次 App），再看 `当前接管方式` 是不是"未接管"，最后看 `最近一次错误`。

## 八、已知限制（实话实说）

1. **没设密码 = 形同虚设**。孩子可以自己打开 App 关掉守护。请务必设置密码。
2. **「强行停止」无法被拦住**：`stopped` 状态会清空全部闹钟/Job 且不投递广播，
   任何代码都不会执行——**不存在自动重启**。设备管理员在多数机型上能让按钮变灰，
   但它可以被取消激活（系统只允许弹警告，没有 API 能要求密码），部分 ROM 甚至不认。
   v1.9 的对策是**追责**（惩罚欠账 + 次数递增 + 时间线留痕），真正锁死只能用 Device Owner。
3. **状态栏下拉无法遮挡**。系统状态栏层级高于悬浮窗，孩子可以从通知栏看到通知（但点进去也是被遮住的）。
4. **被划掉后最长有约 15 秒的空窗**（保活闹钟的周期）。想彻底消掉这段时间，就做系统里的
   「最近任务加锁」——加锁后系统直接不允许划掉。
5. **如果系统限制特别严**（把应用的闹钟全部延迟），可能退化到 5 分钟才复活一次。
   所以第五节那些系统设置要认真做，它们比代码更管用。
6. **状态栏会出现一个小闹钟图标**——这是 5 分钟强通道（`setAlarmClock`）带来的，
   它是唯一不会被省电策略延迟的闹钟类型。介意的话告诉我，可以去掉，但保活强度会下降一档。
7. 本应用控制的是**平板自身**的使用时间。如果你说的"电脑"指的是另一台 Windows 电脑，那需要完全不同的方案（Windows 端要有代理程序），这个 APK 不适用。
8. **极少数应用不理会音频焦点**（个别小厂播放器、部分游戏的背景音），这时前面的手段都停不住它。
   解决办法有两个：给「通知使用权」（可以直接下发暂停），或者打开「兜底：静音」。
   前者更干净，后者只是没声音、视频还在跑。

## 八·五、版本修复记录

### v2.1.1（当前）

**修的是"后台只能看到打开次数、看不到使用时长"。**

根因在采集侧：`Usage.collect` 每次上报都把"当前这一段"的起点取成本轮窗口的起点
（上一轮心跳的时刻）。于是孩子连着用同一个应用时，每 20 秒就新开一条记录，
一小时攒 180 条首尾相接的碎片。服务端按 `(start, pkg)` 幂等覆盖，
起点一直在变 → 覆盖永远命中不了 → 碎片全部落库。

两个后果：

- 时间轴上几百个几秒的小色块挤在一起，看起来"所有应用叠成一团"；
- 时长统计被切碎后失真（页面上的 0m 另有原因，见服务端 v2.1.1）。

修法：把"当前段的起点 + 包名"持久化到 `Prefs.usageSegStart` / `usageSegPkg`，
每次心跳带进去；**只要应用没换，起点就一直用第一次记下的那个**。
这样同一段每次上报都命中同一条记录，`end` 往后推，时长连续累加。

顺带修了熄屏的处理：原来熄屏只把游标推到当下，亮屏后仍会把整段熄屏时间
算进"最近使用"。现在熄屏时把游标置 0 并清空当前段，亮屏后只从最近 30 秒起算。

### v2.1.0

两件事：**主界面瘦身** + **前台应用采集（给后台时间线用）**。

#### 1. 主界面只留四样东西

| 位置 | 内容 |
| --- | --- |
| 状态卡 | 守护状态 + 本轮使用进度条 |
| 开关 | 开启 / 停止守护 |
| 今日 | 今日已用 X 分钟 · 强制休息 N 次 |
| 入口 | ⚙ 设置 / ☁ 远程管理 / 🩺 诊断与测试 |

时长、密码、权限自检、防破解、静音兜底、远程管理、测试、说明、诊断
全部收进「设置页」（`settingsView`），点入口滑进去，左上角返回或按返回键回主界面。
**没有拆成第二个 Activity**：密码门禁是绑在 `MainActivity` 生命周期上的
（`onResume` 重新上锁、`onStop` 隐藏内容），拆页会把这些状态拆散，
反而更容易出 v2.0.1 那种"上锁期间碰到没初始化的控件"的崩溃。

#### 2. 前台应用采集

`Usage.kt`，用系统的 `UsageStatsManager.queryEvents()`：

- 需要 **`PACKAGE_USAGE_STATS`（使用情况访问）**，是**可选**权限。
  没授权时只是不上报应用名，守护、时间线里的"在线时段"都照常工作。
  设置页「应用使用记录（时间线）」一行有状态和一键跳转。
- 只记**切换点**：相邻同包合并（Activity 之间跳转会连报），过滤系统 UI / 锁屏 /
  自己的包，最后生成 `[start, end)` 片段。
- **每 20 秒随心跳增量上报**，游标 `usageCursor` 只在**上报成功**后推进 ——
  断网时下次自动补上，不会漏掉孩子中间用过的应用。
- **熄屏不采集**：熄屏后系统不会关闭任何应用，最后一个前台应用一直挂着，
  照常上报会把整晚算成"在用 B 站"。熄屏时直接跳过并推进游标。
- **长时间用同一个应用**（看视频一小时没切过）：窗口内没有任何 `queryEvents` 事件，
  这时用上次记住的包名接上；进程刚起来没记住，才回溯 12 小时找一次。
- `AndroidManifest` 加了 `QUERY_ALL_PACKAGES` —— Android 11+ 的包可见性限制，
  不加连应用名都查不到，只能显示包名。侧载分发不受商店政策限制。

> 为什么用系统记录而不是自己监听 Activity：`queryEvents` 由系统记，
> **不依赖我们的进程活着**。就算守护被冻结、被杀，之后能跑一次，
> 中间这段时间的切换也照样能补回来。

### v2.0.2

**修的是"推到后台后，通知栏里的计时两三秒就不动了"。**

先说结论：这**不是崩溃，也不是计时写错**，而是 OPPO（ColorOS）把后台进程**冻结**了。
前台服务 + 常驻通知只能保证进程**不被回收**，保证不了它**一直在跑**。
`应用速冻` / `睡眠待机优化` 会把整个进程挂进 cgroup freezer，线程全部暂停 ——
通知栏还挂着（通知是 SystemUI 画的），里面的数字自然就停在冻结那一刻。

三个改动，正好对应"看清它 / 绕过它 / 不再被骗"：

| 改动 | 目的 |
| --- | --- |
| **tick 停滞检测** | `tick` 里记录两次节拍的实际间隔，超过 3 秒就记一笔（次数 + 最长值）。诊断区新增「后台停滞：N 次（最长 X 秒）」，直接给出冻结证据 |
| **到点闹钟**（`KeepAlive.armDeadline`） | 把"用满上限那一刻"交给系统 `setAlarmClock`。闹钟在系统侧，进程被冻结也照样投递（投递时系统会临时解冻并给白名单），到点把服务叫醒、弹遮罩。**这是"应用被冻结时守护依然有效"的根本保障** |
| **通知改用系统 Chronometer** | 秒数由 SystemUI 自己刷，不再依赖我们每秒 `notify`。进程被冻住时数字照样在走 —— 到底是流程卡了还是进程冻了，一眼能分清；顺带避开国产 ROM 对通知高频更新的节流 |

另外两处细节：

- `tick` 里的 `step()` 加了 `try/catch`。原来写的是 `step(); postDelayed(...)`，
  一次异常就等于**计时节拍永久停摆**，而通知还挂着 —— 看起来"在跑"，其实全停了。
  现在异常只记日志，节拍继续。
- 「到点闹钟」不需要频繁重排：计时正常时 `now + 剩余时长` 恒等于同一个时刻，
  用 15 秒阈值挡掉抖动；熄屏（计时本来就暂停）、进入休息、关闭守护时都会撤掉。

**家长要做的（OPPO / ColorOS）**：设置 → 电池 → 应用速冻 → 把「使用守护」设为**不优化**；
再到 应用管理 → 使用守护 → 耗电管理 → 打开「允许后台活动」「允许自启动」。
设置页的「电池优化」按钮能直接跳到系统白名单页。做完之后诊断区应该是：

```
电池优化：已在白名单（后台可自由运行）
后台停滞：未发现（计时节拍正常）
```

### v2.0.1

**修的是 v2.0 的一个致命崩溃：设了家长密码的设备，"点开就退出"。**

原因很具体：`renderRemote()` 是 v2.0 新加的函数，每秒刷新时都会被调用，
但它忘了判断控件是否就绪。而**设了家长密码时，`onCreate` 只弹密码框、不执行
`setupUi()`** —— 所有 `lateinit` 控件都还没赋值。于是：

```
onCreate → 藏内容 + 弹密码框
onResume → handler.post(uiTick)     ← 不等密码，立刻跑
uiTick   → renderStatus/renderDiag/refreshPermissions 都有 isInitialized 判断，安全返回
         → renderRemote() → btnRemoteSync.isEnabled   ← ★ UninitializedPropertyAccessException
```

结果是密码框刚弹出来，进程就被异常带走了 —— 从用户角度看就是"点开就闪退"，
而且**每次打开都闪**，因为密码一直存在。v1.9 及更早的版本没有这段代码，所以没这个问题；
从旧版升级上来（SharedPreferences 保留，密码还在）就会立刻中招。

同批修的还有三处：

| 问题 | 修法 |
| --- | --- |
| 上锁时把 `android.R.id.content` 设成 `INVISIBLE`，万一密码框没弹出来就是**一片空白**，和闪退一模一样 | 加一层不透明的「🔒 已上锁」遮片挂在 DecorView 上，至少能明确"应用还在、只是要密码" |
| 密码框被收掉却没验证通过（系统回收窗口等）→ 停在空白页 | `onDismissListener` 里检查 `unlocked`，没解锁就直接 `finish()`，不留半死状态 |
| `startForeground()` 失败后服务继续留在"未提升为前台"的中间态 | 系统会在约 5 秒后抛 `RemoteServiceException` 干掉整个进程。现在失败**立刻 `stopSelf()`** |

另外补了两样东西：

- **崩溃自记录**（`Crash.kt` + `GuardianApp.kt`）：接住未捕获异常，把时间、机型、版本、
  完整堆栈写进 `files/last_crash.txt`；诊断区显示一行摘要，测试区多了「查看上次崩溃日志」，
  可一键复制。以后出问题不用教家长开 USB 调试跑 `adb logcat`。
- `uiReady` 从 `setupUi()` 开头挪到结尾 —— 它代表"控件全部就绪"，放开头的话
  中途抛异常会让每秒刷新去访问半初始化的控件，把小问题放大成闪退。

**加了"远程管理"：平板上报状态，网页上远程锁定/解锁/改配置。**

服务端是配套的 `GuardianServer`（Rust，单文件静态二进制，见那边的 README）。
App 这边新增的只有三件事：

| 改动 | 文件 | 说明 |
| --- | --- | --- |

1. **服务器地址就在 App 里配**，不用改代码、不用重装。地址框允许写

2. **配对了才联网**。没配对时一个请求都不发，`INTERNET` 权限闲着。

3. **指令是设备主动来取**（20 秒一次），不是服务端推送。家里平板在 NAT 后面没有公网地址，
   国内也收不到 FCM，只有这条路可靠。代价是后台点完按钮最多等 20 秒。
4. **关闭守护后仍保持心跳**（"远程待命"）：否则服务一停就再没有心跳，

5. **今日累计时长是新加的**（`todayUsedMs`），口径与计时器一致：亮屏 + 已解锁 + 不在休息；
   每 5 秒落一次盘，跨天自动归零。后台首页的"今日使用总时长"就是它。
6. **明文 HTTP 是故意允许的**（`android:usesCleartextTraffic="true"`）：
   局域网 `http://192.168.x.x:8000` 是主要用法，不允许就根本连不上。
   公网请用 HTTPS 反代，见服务端部署文档第六节。

> 安全边界：**设备令牌等同于这台平板的密码**，拿到它就能读状态、下发锁定。
> 所以它只存在私有目录、任何界面都不显示；后台"删除这台设备"之后令牌立刻失效，
> App 会显示"设备令牌已失效，请重新配对"。

### v1.8

**修的是"画面挡住了，声音还在"：孩子看视频到点弹遮罩，视频在后台继续放。**

先把结论说清楚：**安卓上第三方应用没有办法"直接暂停别人的播放器"**（那是别的应用的进程）。
但有三条公开、合法的路可以走，按效果从好到差排：

| 层级 | 手段 | 需要什么 | 效果 |
| --- | --- | --- | --- |
| ① 音频焦点 | `AudioManager.requestAudioFocus(AUDIOFOCUS_GAIN)` | **什么都不需要** | 正在播放的应用收到 `AUDIOFOCUS_LOSS`，**主动暂停**。接电话时音乐自动停、网易云被抖音打断，用的都是这套机制 |
| ② 媒体会话 | `MediaSessionManager.getActiveSessions()` → `transportControls.pause()` | 「通知使用权」（家长在设置里点一下授权） | 能真正给播放器下发"暂停"指令，连不理会音频焦点的应用也能停住 |
| ③ 系统音量 | `setStreamVolume(STREAM_MUSIC, 0)` | 什么都不需要 | 只是"没声音"，视频还在解码耗电。**默认关闭**，作为最后兜底 |

实现要点（`Silence.kt`）：

1. **音频焦点是主力**。B 站、腾讯视频、爱奇艺、优酷、YouTube、抖音、浏览器网页播放器
   都实现了焦点协议，所以第一层就能覆盖绝大多数情况，**而且不需要任何权限**。
2. **焦点必须一直持有到休息结束**。这样不只是"停一次"——孩子就算去点播放，
   别的应用也拿不到焦点、播不出声。休息结束才 `abandonAudioFocusRequest`，
   对方收到 `AUDIOFOCUS_GAIN` 会自动续播。
3. **每 3 秒重新压制一次**。视频 App 被暂停后可能自动播下一集，压一次不够。
   服务本来就在每秒跑计时循环，顺手做这件事，不额外耗电。
4. **音量兜底做了"防残留"**：原音量与"是我们静的音"这个标记**一起 `commit()` 同步落盘**。
   进程若在静音中被强行结束，下次服务启动（`Silence.recoverIfStuck`）会把音量恢复回来，
   不会出现"平板永远没声音、家长以为坏了"。休息途中家长关掉这个开关也会立刻恢复。
5. **新增 `MediaWatchService`（通知监听服务）**：它不重写任何一个通知回调，
   **不读取、不保存、不上传任何通知内容**，存在的唯一理由是通过系统审查拿到媒体会话列表。
   没授权时系统根本不绑定它，功能自动降级为"只用音频焦点"，不影响任何其它功能。
6. 遮罩与兜底界面顺带**吃掉了音量键**，否则"兜底静音"会被按一下音量键顶掉。

设置界面新增一栏「休息时让视频安静下来」，两个开关 + 一个「通知使用权」状态行；
诊断信息新增一行 `休息静音：音频焦点持有中 · 通知使用权未授 · 已暂停 1 个播放器`，
孩子反馈"还是有声音"时，看这一行就知道是哪一层没生效。

> 为什么不做成"一进来就降到最低音量"？因为那是**系统级**改动：只管没声音、视频还在跑，
> 而且异常退出时可能把音量留在 0。所以它被放在最后，默认关闭，由家长按需打开。

### v1.7

**修的是"家长根本输不进密码"：点密码框时系统键盘闪一下就消失了。**

| 问题现象 | 根因 | 修法 |
| --- | --- | --- |
| 强制休息遮罩上点「家长操作」→ 点密码框，**键盘闪一下就没了，连看都看不清**，密码输不进去 | 遮罩是 `TYPE_APPLICATION_OVERLAY` 的全屏系统悬浮窗，**层级比输入法窗口还高**（而且是不透明的）。系统输入法的键盘窗口刚起来就被遮罩盖住/挤掉；少数 ROM 上还会因为遮罩抢走焦点而直接把键盘收回去。设置界面那个密码框虽然在普通 Activity 里，但在做过管控的平板上同样可能弹不出来——**一旦弹不出来，家长就彻底进不去应用了** | 三处密码输入（遮罩、门禁、设置密码）**全部改用应用自绘的数字键盘**：新增 `PinPad.kt`，用 `TextView` + 自绘圆角背景画 3×4 键盘，**完全不依赖系统输入法**。遮罩的 `overlay_lock.xml` 里已删掉 `EditText` |

顺带解决了两件事：

- **家长密码不会被第三方输入法记录/联想/上传了**——键盘是自己画的，密码从来不经过输入法进程。
- 遮罩内容变高（要放下键盘），所以整个遮罩套了一层 `ScrollView`，小屏设备上也不会被裁掉。

另外补了两道保险：

1. **操作限时**：家长输对密码后，两个操作按钮（跳过本次休息 / 暂停守护）**只在 60 秒内有效**，
   超时自动重新上锁。防止家长验证完走开、孩子顺手把休息跳过。
2. **试错限流**：连续输错 5 次 → **冷却 60 秒**，冷却期内一律不校验。
   这一条是必须的：之前系统键盘弹不出来，孩子连试都没法试；现在键盘能用了，
   4 位数字只有 1 万种组合，不限流等于把门敞开。计数与冷却都写进持久化存储，
   **杀掉应用重启也不会清零**。换密码时会自动清掉计数。

> 老版本可能设过超过 8 位的密码（当时设置界面的输入框没有长度上限），
> 新键盘的输入上限取"目标位数"，所以照样能输满、不担心被锁在外面。

### v1.5

**修的是一个安全漏洞：把应用"隐藏"再打开，不需要重新输密码。**

| 问题现象 | 根因 | 修法 |
| --- | --- | --- |
| 按 Home 键把应用隐藏，再从桌面 / 最近任务打开，直接就是设置界面，**不要求输密码** | 密码框只在 `onCreate()` 里弹。而 `MainActivity` 在清单里是 `launchMode="singleTask"`，**"隐藏"并不会销毁 Activity**——重新打开只是把已有实例拉回前台，只走 `onStart` → `onResume`，`onCreate` 不会再执行，于是密码框永远不再出现 | 每次回到前台（`onResume`）都检查一次"这次有没有验证过"，没有就重新弹密码框 |

要挟路径很直接：家长设好密码 → 打开应用 → 按 Home 键放下 → 孩子拿起设备，
从最近任务一点，就拿到一个**完全解锁**的设置界面，能直接把守护开关关掉。
这不是"防护弱了一点"，是**防护事实上被绕过**。

配套的两点：

- **验证通过前，设置内容整体隐藏**（`setContentVisible(false)`）。
  原来密码框背后就能看到全部设置项，现在只看到一张空屏 + 密码框。
- **两道"离开"信号都上锁**：`onStop()`（切到别的应用 / 熄屏）和
  `onUserLeaveHint()`（按 Home / 按最近任务键）。
  后者是用户主动离开时才有的回调，比 `onStop` 更精确——我们自己 `startActivity`
  跳去系统设置页**不会**触发它。

**一个刻意的例外**：家长点「去设置」去授权（悬浮窗 / 通知 / 电池 / 设备管理器）时，
故意不重新上锁——否则光走完授权流程就要来回输四五遍密码。
实现是给这次跳转记一个时间戳（不是布尔标记，会自己过期）：

- 跳转后 **8 秒内**发生的 `onStop` 才算"这次主动跳转"；
- 回到前台若距跳转不足 **3 分钟**，视为同一次操作，不重新验证；
- 超过 3 分钟（说明人可能已经走了、设备也可能被拿走）→ 照样重新验证。

### v1.4

**修的是保活机制的根本缺陷——它以前完全依赖"ROM 会不会回调"。**

| 问题现象 | 根因 | 修法 |
| --- | --- | --- |
| 手动结束应用后，等十几秒也不自动复活 | 复活闹钟是在 `onTaskRemoved()` / `onDestroy()` 里排的，而国产 ROM 结束应用时是**直接 SIGKILL，两个回调都不执行** → 复活闹钟根本没被排上，只剩一条 60 秒心跳兜底 | 改成**永续自检**：系统里永远挂着一个 **15 秒**的闹钟，它到点叫醒服务、服务再排下一次。这条链不依赖任何回调 |
| 自检按钮能复活、手动结束却不能 | 自检是在进程被结束**之前**主动排的闹钟；手动结束时没人排 | 同上（现在两者走的是同一条主通道） |
| 上一条的连锁反应：重开 App 会立刻进一次休息 | `serviceAlive` 标记残留 → 被判为"非正常退出" → 触发惩罚。这其实**证明**了 `onDestroy` 没执行 | 保留（这是正确行为），但现在惩罚原因会写清楚是"非正常退出"还是"强行停止" |

新增的加固：

- **强通道 `setAlarmClock`（5 分钟）**：唯一不会被 Doze / App Standby 延迟的闹钟类型，
  且触发时系统会给应用临时白名单以便启动前台服务。代价是状态栏多一个小闹钟图标。
- **「强行停止」自动识别**：启动时用 `PendingIntent.FLAG_NO_CREATE` 查"我们排的闹钟还在不在"，
  查不到就说明应用被置成了 `stopped` 状态（强行停止会清空全部闹钟），诊断区会明确报出来。
  这是唯一无法自救的情况，必须让家长知道。
- **诊断区大扩充**（从 5 行到 11 行）：保活通道状态、最近一次启动来源、**上次中断时长**、
  卡片被划掉次数、强行停止次数、启动失败原因。
  其中「上次中断时长」是判断保活到底灵不灵的核心指标。
- `GuardianService.start()` 与 `startForegroundSafely()` 的异常不再往上抛——
  调用方是闹钟/任务调度，一崩整条保活链就断了；现在一律记录到诊断区。

### v1.3

| 问题现象 | 根因 | 修法 |
| --- | --- | --- |
| 退出后重新打开 App，一直停在"守护未在运行"，必须手动关开一次开关 | 服务只在**切换开关**和**开机广播**时启动，应用打开时不会自动拉起 | `MainActivity` 每秒检查一次「开关开着但服务没跑」，发现就自动启动（最多重试 5 次） |
| 开着"被强制结束后立即休息"也没反应 | 判断条件只有"心跳中断 > 3 分钟"，而划掉卡片后服务几秒内就重启了，**间隔永远不够** | ①改用"运行标记是否被正常清除"作为主判据（进程被强杀时 `onDestroy` 不会执行，标记残留，**立刻可判定**）；②在 `onTaskRemoved` 里**直接**触发惩罚，不再等重启后再判断 |

另外做了两处加固：

- 复活通道从 1 条加到 4 条（3 个闹钟 + JobScheduler 一次性任务 + 15 分钟看门狗）。
- 修正一个隐患：`detectKill` 原本在每次 `onStartCommand` 都跑，而心跳闹钟每 60 秒触发一次，
  会把"正在正常运行"误判成"上次死于非命"，导致每分钟误触发惩罚。现在限制为**每个进程只判断一次**。
